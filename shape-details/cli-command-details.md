# Command Definition Keys

This document defines the purpose, responsibility, and expected behavior of each key stored within a command definition object.

---

# id

## ROLE:
Provides the permanent machine-readable identity for a command.

## STRATEGY:
Used by consumers for lookup, indexing, searching, and referencing commands without relying on display names.

## INVARIANT:
The value must be unique within the content registry.

Once published, the identifier should remain stable because external systems may depend on it.

---

# shortDescription

## ROLE:
Stores a concise summary intended for compact CLI displays, tables, and quick-reference views.

## STRATEGY:
Provides the primary purpose of a command in a single readable sentence.

## INVARIANT:
Short descriptions should explain the command's intent.

They should:
- remain brief and scannable
- avoid repeating the full description
- avoid including the executable command payload
- avoid implementation details
- describe the user-facing value of the command

## FORMAT:
Recommended length: 5-10 words.

Examples:

GOOD:
"Shows directories only in a tree layout."
"Finds unused project dependencies."
"Clears the Next.js build cache."

BAD:
"tree -d displays the directory structure..." ❌
"Runs the command tree -d..." ❌
"Uses a recursive filesystem traversal algorithm..." ❌

--

# title

## ROLE:
Provides the human-readable name displayed to users.

## STRATEGY:
Optimized for terminal output, documentation, search results, and interface rendering.

## INVARIANT:
The title may change without affecting command references because it is not used as the primary identifier.

---

# command

## ROLE:
Stores the executable command string represented by the definition.

## STRATEGY:
Acts as the primary execution payload that can be copied, displayed, or passed to execution layers.

## INVARIANT:
Contains only the command syntax.

Should not contain:
- terminal prompts
- output examples
- markdown formatting
- explanations

---

# description

## ROLE:
Explains the purpose and behavior of the command.

## STRATEGY:
Provides context for users discovering commands through search, documentation, CLI help, or other interfaces.

## INVARIANT:
Should describe what the command does.

Should not describe how the interface displays the command.

---

# exampleOutput

## ROLE:
Stores representative output generated by the command.

## STRATEGY:
Allows users and interfaces to preview expected results without executing the command.

## INVARIANT:
Output should represent realistic example data.

It should remain static and should not depend on live machine state.

---

# tags

## ROLE:
Provides searchable metadata labels associated with the command.

## STRATEGY:
Enables flexible discovery and filtering without forcing commands into rigid categories.

## INVARIANT:
Tags should describe meaningful concepts such as:

- technology
- workflow
- purpose
- environment
- use case

Tags should not duplicate the title or description.

---

# platform

## ROLE:
Defines the operating systems where the command is expected to function.

## STRATEGY:
Allows consumers to filter commands based on environment compatibility.

## INVARIANT:
Values represent operating systems only.

They do not represent:

- shells
- terminal applications
- package managers
- editors

---

# shell

## ROLE:
Defines the shell interpreter required to correctly parse and execute the command.

## STRATEGY:
Allows execution layers to understand syntax compatibility before running commands.

## INVARIANT:
Represents the command interpreter only.

It does not describe the terminal emulator being used.

---

# availability

## ROLE:
Defines where the command dependency originates.

## STRATEGY:
Allows consumers to determine whether additional installation steps are required.

## INVARIANT:
Represents dependency source only.

It does not describe command safety or execution risk.

---

# risk

## ROLE:
Defines the potential impact of executing the command.

## STRATEGY:
Allows interfaces to provide warnings, confirmations, or additional safeguards before execution.

## INVARIANT:
Represents operational impact only.

It does not determine whether a command is valid or supported.

---

# notes

## ROLE:
Stores additional context, warnings, requirements, and usage guidance.

## STRATEGY:
Provides supporting information that does not belong inside the main description.

## INVARIANT:
Notes should enhance understanding.

They should not contain the executable command payload.

---

# links

## ROLE:
Stores external references related to the command.

## STRATEGY:
Allows consumers to provide additional documentation, repositories, tutorials, or resources.

## INVARIANT:
Links should provide supporting information only.

They should not replace the command definition itself.
